## 1. Product summary
 
FacilityDesk lets **facility management (FM) companies** sign up as tenants, register their **client sites**, and handle every complaint as a tracked **work order** with an **SLA** (response and resolution deadlines).
 
One codebase, one database, many tenants. **A tenant must never see another tenant's data** — this is the most important rule in the system.
 
### Users
 
| Role | Belongs to | Can do |
|---|---|---|
| Super Admin | Platform (no tenant) | Manage tenants, plans, suspend tenants, view platform stats |
| Tenant Admin | One tenant | Everything inside their tenant: users, roles, masters, SLA config, reports, audit log |
| Supervisor | One tenant | Raise, assign/reassign, change status, close/reopen work orders; team reports |
| Technician | One tenant | See and update **only jobs assigned to them**; upload before/after photos |
| Client User | One tenant + one client | Raise work orders for their own client's sites; view them; confirm (close) or reopen resolved ones |
 
### Out of scope for v1
Native mobile app, tenant billing/payments, IoT, multi-language UI.

  Livewire/             WorkOrderBoard, WorkOrderTimeline, DashboardStats, ...

### 3.2 Layering
- **Form Requests** validate input.
- **Policies** authorize every action (web and API).
- **Action classes** hold business rules; both web and API controllers call the same Action.
- **Events** are fired by Actions; side effects (notifications, history, cache busting) happen in **queued listeners**.
- **API Resources** shape all JSON output.
### 3.3 Multi-tenancy (single database, `tenant_id` column)
1. `IdentifyTenant` middleware resolves the tenant from the **subdomain** (`acme.facilitydesk.test`) for web, and from the **authenticated user** for API. Store it in a request-scoped singleton `TenantContext` (`id()`, `tenant()`, `set()`, `clear()`).
2. `EnsureTenantIsActive` blocks suspended tenants.
3. Every tenant-owned model uses the `BelongsToTenant` trait:
```php
trait BelongsToTenant
{
    protected static function bootBelongsToTenant(): void
    {
        static::addGlobalScope('tenant', function (Builder $query) {
            $tenantId = app(TenantContext::class)->id();
            if ($tenantId !== null) {
                $query->where($query->getModel()->qualifyColumn('tenant_id'), $tenantId);
            }
        });
 
        static::creating(function ($model) {
            $model->tenant_id ??= app(TenantContext::class)->id();
        });
    }
 
    public function tenant(): BelongsTo
    {
        return $this->belongsTo(Tenant::class);
    }
}
```
 
4. **Queued jobs and listeners** that touch tenant data must carry `tenantId` and restore `TenantContext` before running (use a job middleware `SetTenantContext`).
5. Console commands that work across tenants either loop per tenant (setting the context) or query explicitly with `withoutGlobalScope('tenant')`.
6. Accessing another tenant's record returns **404, never 403**.
7. Spatie permission `team_id` is set to the current tenant in `IdentifyTenant`.

## 4. Database
 
### 4.1 Conventions
- PK: `$table->id()` (BIGINT UNSIGNED).
- FKs: `foreignId(...)->constrained()`. `cascadeOnDelete()` only for rows meaningless without the parent (comments, histories, pivots); otherwise restrict and use soft deletes.
- Every tenant table has `tenant_id` NOT NULL, FK → `tenants`, and `tenant_id` is the **first column of every composite index**.
- Uniqueness is **per tenant** (e.g. UNIQUE `(tenant_id, email)`).
- Enums stored as `VARCHAR(20)` and cast to PHP backed enums (not MySQL ENUM).
- All timestamps in **UTC**; display in the site's timezone.
- Soft deletes on: clients, sites, locations, assets, work_orders, users.
- Use `Relation::enforceMorphMap()` for polymorphic types.

## 5. Work order lifecycle
 
`WorkOrderStatus` backed enum: `open`, `assigned`, `in_progress`, `on_hold`, `resolved`, `closed`, `cancelled`.
 
Allowed transitions (implement `canTransitionTo(self $to): bool` on the enum):
 
| From | To |
|---|---|
| open | assigned, cancelled |
| assigned | in_progress, assigned (reassign), cancelled |
| in_progress | on_hold, resolved |
| on_hold | in_progress |
| resolved | closed (client/supervisor confirms), assigned (reopen) |
| closed | — |
| cancelled | — |
 
Rules:
- All transitions go through the `ChangeStatus` action, which checks the enum, checks the policy, writes a `work_order_status_histories` row, and fires `WorkOrderStatusChanged`.
- First move to `in_progress` sets `responded_at`.
- Moving to `resolved` requires `resolution_note`, sets `resolved_at`.
- Moving to `closed` sets `closed_at`.
- Time spent in `on_hold` is added to `hold_minutes` and pushes `resolution_due_at` forward by the same amount.
- Reopen and cancel require a note.
### SLA
- `SlaCalculator` (pure PHP service, fully unit-tested) sets `response_due_at` and `resolution_due_at` from the tenant's `sla_policies` row for the priority, at creation time.
- Response is breached if `responded_at` is null and now > `response_due_at`.
- Resolution is breached if status not in (resolved, closed, cancelled) and now > `resolution_due_at`.

## 6. Features by module (MVP)
 
1. **Tenant onboarding** — public signup form (company name, slug, admin name/email/password) → creates tenant, seeds roles, permissions, 4 SLA policies, default categories (Electrical, Plumbing, HVAC, Housekeeping, Civil, Security), and the Tenant Admin user, inside one DB transaction.
2. **Auth & users** — login (tenant subdomain), logout, password reset, email verification, invite user by email (signed link to set password), assign role, deactivate user.
3. **Masters** — CRUD for clients, sites, locations (tree UI), categories, SLA policies, assets (with QR code image generated from `qr_token`), technician skills, site coverage.
4. **Work orders** — list with filters (status, priority, site, category, assignee, date range, breached only), search by number/title, create (with up to 5 photos), detail page (info, timeline of status history, comments with internal flag, attachments), assign/reassign, status changes, close/reopen.
5. **Technician view** — "My jobs" sorted by `resolution_due_at`, quick status buttons, photo upload.
6. **QR flow** — `/a/{qr_token}` (authenticated) shows the asset and its open work orders, with "Raise work order" prefilled.
7. **Notifications** — mail + database channels: assigned (to technician), resolved (to raiser), SLA breach (to site supervisor + tenant admins). Bell icon with unread count.
8. **Dashboard** — open/closed counts, SLA compliance % this month, breached count, jobs per technician, top categories; filter by site and date range. Cached per tenant in Redis for 5 minutes, busted on work order events.
9. **Reports** — monthly PDF and Excel per client, generated as a `Bus::batch()` with progress shown on the Reports page; download link when done.
10. **Audit** — activity log on work orders, users, roles; Tenant Admin can view and filter it.

## 9. Security checklist (must all be true)
 
- Tenant scope + policies on every model; tests prove cross-tenant 404s (web and API).
- Explicit `$fillable`; `tenant_id`, `status`, `assigned_to`, `number` never mass-assigned from requests.
- Uploads: jpg, png, webp, pdf only; max 5 MB; stored outside `public/`; signed URLs.
- Rate limiting on login and API.
- CSRF on web; Sanctum on API; CORS restricted.
- Security headers middleware (CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy; HSTS in production).
- Internal comments never returned to Client Users (policy + resource).
- `APP_DEBUG=false` in production config.
## 10. Performance checklist
 
- `Model::preventLazyLoading(! app()->isProduction())`.
- Eager load in every list query.
- Indexes as in section 4.
- `cursorPaginate()` for the technician feed.
- Dashboard cached per tenant.
- Reports and exports only in queued jobs.
- Seeder that can create 50,000 work orders (`DemoSeeder --large`) to benchmark list queries; record before/after timings in README.
